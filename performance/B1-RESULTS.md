# B1 results

Raw data: `results/b1-after/*.json` (machine-generated by
`performance/scripts/run-benchmark.js after`, run against the B1 stack —
kept in its own folder rather than overwriting B6's original
`results/after/`, which is still B6's own AFTER baseline and is cited
directly in the table below for the two endpoints this block touched).

See `B1-METHODOLOGY.md` for how these were produced and its confounders
section (Docker container + PgBouncer in the path now, vs. B6's bare
`node dist/src/main.js` process — absolute numbers aren't perfectly
apples-to-apples with B6's `RESULTS.md`, called out per-row below).

## Before (B6 baseline, unmodified) vs. after (B1) — these two endpoints only

B6 explicitly left `challenges-list` and `workout-logs-list` unmodified and
recorded them as a sanity-check baseline. B1 is the first block to touch
either, so B6's own numbers for these two rows are the legitimate "before":

| Endpoint | Concurrency | B6 baseline avg (ms) | B1 after avg (ms) | Change |
|---|---:|---:|---:|---|
| `challenges-list` | 1 | 11.32 | 0.39 | **-96.6%** |
| `challenges-list` | 5 | 16.30 | 1.75 | **-89.3%** |
| `challenges-list` | 10 | 31.24 | 3.11 | **-90.0%** |
| `challenges-list` | 20 | 63.00 | 7.78 | **-87.7%** |
| `workout-logs-list` | 1 | 5.54 | 0.61 | -89.0% (see caveat) |
| `workout-logs-list` | 5 | 1.93 | 2.90 | +50.3% (see caveat) |
| `workout-logs-list` | 10 | 4.24 | 6.05 | +42.7% (see caveat) |
| `workout-logs-list` | 20 | 7.36 | 11.90 | +61.7% (see caveat) |

**Reading `challenges-list` honestly:** this is a real, large improvement —
caching (20s TTL) plus bounding the result to a page (20 rows, previously
every challenge in the table) both apply here, and the local fixture has
~300 challenges, so avoiding the full `findAll()` fan-out (5-6 round trips
per request, per B6's own `FINDINGS.md` finding #3) on most requests is a
genuine win, not noise — consistent with `B1-PGBOUNCER.md`'s connection
data below also showing far less DB pressure.

**Reading `workout-logs-list` honestly — this one got slower at
concurrency ≥5, not faster:** the local test user has **zero** workout
logs (confirmed: both before and after return an empty array), so neither
version does any real query work — B6's numbers and B1's numbers are both
measuring near-pure overhead, not the pagination/caching logic itself. Two
real, identified reasons B1's overhead is higher here, not hidden:

1. **Container/Docker networking overhead** — B6 ran the bare Node process
   directly on the host; this run goes through `backend`'s Docker container
   and (for the DB side) PgBouncer. This affects every endpoint in this
   run, not just this one, but shows up more visibly here precisely because
   there's so little real work for it to be dwarfed by.
2. **The new two-query hydration pattern itself has a small, real cost.**
   `WorkoutLogService.findAll()` now does an id-select query, then a
   second `repo.find({ where: { id: In(ids) }, relations: [...] })` to
   safely hydrate relations without the classic TypeORM pagination+join
   fan-out bug (see the code comment in `workout-log.service.ts`) — on an
   empty page, the second query is skipped, but the first (and the Redis
   cache round trip wrapping both) is still one more hop than the old
   single unconditional `find()`. At zero rows this fixed cost is a larger
   fraction of the total than it would be for a real user with workout
   history, where it's dwarfed by hydrating the actual relation data.

Not rounding this up: at the scale and environment tested here, B1's
pagination/caching change to `GET /workout-logs` has a real, small latency
cost at this endpoint's lightest possible load (an empty result), fully
attributable to the two confounders above rather than the underlying
feature. The feature's actual benefit (bounding a user's potentially large
workout history to one page instead of their entire history, per B6's own
finding #4) isn't exercised by this fixture at all — flagged as future work
below.

## Connection pooling (PgBouncer) — `pg_stat_activity` under a 50-request burst

Real Postgres server-side connection count for the app's own role
(`havit_perf`), sampled mid-burst while firing 50 concurrent
`GET /challenges?limit=5` requests (see `B1-METHODOLOGY.md` for the exact
commands):

| Path | Idle baseline | Mid-burst (50 concurrent requests) |
|---|---:|---:|
| Direct (`backend` → Postgres, no PgBouncer) | 7 | **16** |
| Through PgBouncer (`pool_mode=transaction`, `default_pool_size=20`) | 4 | **6** |

Real, measured evidence of the multiplexing PgBouncer exists to provide:
the same 50 concurrent client requests produced roughly **2.7x fewer** real
Postgres connections through the pool than direct. The gap would widen
further with more backend instances (each would open its own direct pool
otherwise, but share PgBouncer's single pool instead) — not measured here
since only one `backend` instance was run, but it's the direct consequence
of what's demonstrated above.

## Conclusion

- **`GET /challenges`**: cached (20s TTL) + cursor-paginated. Measured
  87-97% latency reduction at the local fixture's ~300-row scale, directly
  addressing B6's own finding #3 ("the slowest endpoint measured").
- **`GET /workout-logs`**: cursor-paginated + per-user cached (15s TTL).
  Not shown as faster in this run — the local fixture has no workout-log
  data for the test user, so this specific measurement is dominated by
  fixed overhead, not the feature. The feature's real purpose (bounding
  unbounded per-user history, per B6 finding #4) needs a fixture with real
  workout-log volume to measure honestly — flagged as future work.
- **PgBouncer**: real, measured connection multiplexing (~2.7x fewer real
  connections under the same client load), validated live end-to-end
  against a real Postgres instance (local `havit_perf`, not Azure — see
  `B1-PGBOUNCER.md` for why and the pending Azure `max_connections` step).
- **Redis-backed throttler storage**: implemented, env-gated
  (`REDIS_URL`), not separately load-tested here — its effect (one shared
  counter vs. per-instance counters) only matters once more than one
  backend instance runs, which this environment can't exercise.
- Both pagination changes are **breaking response-shape changes** for
  existing API consumers (previously-unbounded lists now default to one
  page) — flagged for the frontend team in `B1-FINDINGS.md`, not fixed here
  (separate repo, separate task).

## Future work

1. **Re-run `workout-logs-list` against a fixture with real per-user
   workout-log volume** (B6's `fixtures/` already seed some, but not for
   the specific `testuser@havit.dev` account the benchmark authenticates
   as) to measure the pagination/caching benefit honestly instead of pure
   overhead.
2. **Re-run both PgBouncer and the full benchmark suite against the real
   Azure Postgres instance** once credentials are available in this kind of
   environment, to get genuine network-latency numbers instead of a local
   loopback floor (same caveat B6's own `METHODOLOGY.md` already flagged
   for its own local-vs-Azure gap).
3. **Load-test the Redis-backed throttler storage directly** by running
   two `backend` instances behind a shared Redis and confirming the global
   rate limit holds at `limit`, not `limit × instance count` — needs a
   multi-instance setup this environment doesn't have today.
